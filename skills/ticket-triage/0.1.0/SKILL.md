# Skill：bug 工单预检诊断（ticket-triage）

## 适用范围

测试提交的 bug 工单预检：服务报错、页面异常、接口失败等。产出供接手开发参考的初步根因分析，不是最终结论。

## 前置条件（先核对，缺了就如实说明）

1. 工单至少有：标题、描述、复现现象。三样都缺 → status=partial，missingMaterial 说明缺工单信息。
2. 需要代码定位但工单没给版本 → 不要猜测代码内容，在 missingMaterial 里说明缺代码版本。
3. 需要复现但工单没有页面入口（entryUrl）→ 不要凭空编造复现步骤当结论，说明缺入口与环境。

## 取证步骤（按问题类型选路径，不要全部执行）

- 服务报错/日志类：先 query_logs 拉时间窗内错误日志 → 从堆栈类名、方法名进 search_code → read_code 核实上下文。
- 页面异常类：若 run_browser_check 可用，先按工单 reproductionSteps 生成受约束计划执行，
  再根据"请求是否发出、响应内容是什么、页面显示什么"决定下一步查前端还是查后端：
  - 请求参数错误/没发出 → 查前端提交代码；
  - 请求正确但响应业务失败 → 转向后端拒绝原因（query_logs + search_code 后端仓）；
  - 响应有新值但页面显示旧值 → 转向前端渲染或缓存。
- 日志与请求关联：优先用 request ID / trace ID 关联；只有时间匹配时，明确标注"弱关联"。

## 判定规则

1. 每条根因假设必须有 evidenceIds 支撑；引用只能用工具返回的证据编号（[E#]），禁止编造。
2. 执行状态与复现状态分开："找不到按钮/登录失效"是执行失败，不等于"未复现"，更不是根因。
3. 置信度反映证据强度：单一日志片段最多 candidate；日志+代码位置一致可 supported；
   verified 必须有复现确认，否则降级 supported。
4. 证据不足时：降级为 candidate，把"还缺什么验证"逐条写进 pendingChecks，不要用确定语气补齐。

## 常见错误（上一版踩过的坑）

- 把"查询报错"当"没有错误日志"：查询失败是材料缺失，必须 partial，不许当有效结论。
- 把执行失败当复现失败：两者对开发意味着完全不同的下一步。
- 超预算仍在补证据：预算透明写在提示词里，规划着用；拿不到的材料写进 missingMaterial。
